Runtime note from that verification: the `bicycle` costing is not serviceable from the WASM
runtime — an 11 km Jakarta bicycle route exceeds the SDK's 300 s maximum operation deadline, where
the pinned native binary answers it instantly, and an 11 km `pedestrian` route takes 56 s against
88 s for the 156 km `auto` case. Route output is unaffected (every case both engines could answer
compared byte-identical, `pedestrian` included), and the likely cause is cache pressure: the SDK
caps the decoded-tile cache at 128 MiB while the two largest tiles in this release are 46.2 MiB and
35.7 MiB, and the native half ran with 256 MiB. The app should not ship bicycle routing from this
runtime build without addressing it.
